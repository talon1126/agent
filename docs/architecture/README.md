## 如何阅读

图 01 表达当前项目结构。图 02 与图 03 表达完整目标设计，使用相同的节点编号和责任划分；目标设计不等同于当前所有能力均已部署。

第三张图沿左侧编号向下阅读，每行从左到右依次是输入、三个处理环节和输出。行末的分支说明澄清、权限不足、数据缺失、工具失败与安全回退如何处理。示例需求仅用于说明流程，不为示例商品编造价格、评论或实验结果。

| 步骤 | 核心问题 | 主要产物 |
| --- | --- | --- |
| 01 接入请求 | 用户说了什么，页面提供了哪些线索？ | 版本化请求与关联标识 |
| 02 身份与授权 | 本轮可读取谁的数据、用于什么目的？ | 身份、用途与授权范围 |
| 03 组装上下文 | 哪些页面、会话、事实和偏好值得使用？ | 带来源、优先级和预算的上下文 |
| 04 维护购物目标 | 必须满足什么，还缺哪些关键信息？ | 硬约束、软偏好与目标版本 |
| 05 规划与执行 | 哪些工具在何时、以什么权限执行？ | 有界执行计划与调用记录 |
| 06 多路召回 | 哪些商品值得进一步核实？ | 去重候选、召回来源与索引版本 |
| 07 事实与过滤 | 当前是否满足预算、规格和可购买条件？ | 统一事实快照、合格候选与剔除原因 |
| 08 排序与混排 | 满足条件的商品中，哪些更适合用户？ | 最终顺序、解释代码与回退记录 |
| 09 比较与校验 | 推荐理由是否有事实和证据支持？ | 经核验的对比、洞察与引用 |

逻辑顺序不意味着每轮机械地遍历十步。计划可跳过无关步骤，商品查询与知识查询可以并行；必要澄清可提前返回，失败按预算恢复或降级。

## 关键协作关系

- **知识与事实**：RAG 提供选购指南、FAQ、政策和品牌知识。商品价格、库存、促销和配送由 Commerce Fact Gateway 从权威来源核实；比较、排序与回答绑定同一事实快照。
- **商品与文档索引**：商品召回面向 canonical 商品实体；知识检索面向文档 Chunk。两者分别管理版本、证据与更新。
- **授权与目标**：本轮明确需求优先于历史推断。画像提供软特征，权限不足时走非个性化路径；模型排序仍受硬约束约束。
- **计划与工具**：Agent 负责意图理解、规划和组织解释；工具逐步授权，有并发、重试、超时和取消上限。知识服务通过持久 MCP stdio 公共契约调用。
- **预览与加购**：结构化响应提供动作预览；用户通过独立接口确认后，校验主体、令牌、幂等和最新价格库存，再调用购物车 API。条件变化需要新的预览与确认。
- **展示与学习**：推荐结果已返回不等于已曝光。界面提供真实展示回执，购买与退货来自可信服务端来源；事件处理、特征构建和排序模型训练异步运行，并分别核对授权用途。
- **运行形态**：主系统使用 Docker Compose；RAG 是 ai-service 内的持久子进程。节点表示逻辑职责，图存储、特征存储和模型服务通过基础设施接口适配。

## 编辑与再生成

- `build_diagrams.py`：SVG 布局和图册生成。
- `agent_flow_content.py`：十步拆解的文字内容。
- `atlas.template.html`：离线查看器、缩放与步骤导航。
- `qa_atlas.js`：浏览器排版检查、导航检查、截图和 PNG 导出。
- `verification.json`：来源摘要、导出尺寸、文字布局与浏览器检查结果。

```powershell
python docs/architecture/build_diagrams.py
```

该命令重建 SVG 与 HTML。PNG 需在浏览器按最新 SVG 重新导出，并检查文字重叠、边界、导航和移动端布局。
